# 增量上下文压缩策略 — 技术文档

## 一、架构设计

### 1. 功能背景

在多轮旅行规划对话中，用户的对话历史会随着交互不断增长。当消息数超过 20 轮时，直接将全部历史作为 LLM 上下文会导致：

- **Token 成本爆炸**：每轮请求携带全量历史，Token 消耗线性增长
- **上下文窗口溢出**：超长历史可能超过模型窗口限制
- **响应质量下降**：过多冗余信息稀释了关键上下文

增量上下文压缩策略解决的核心问题是：**在保留关键信息的前提下，控制每次 LLM 调用的上下文长度，使 Token 消耗保持恒定级别（O(1)），而非随对话轮次线性增长（O(n)）。**

### 2. 整体架构

```
┌──────────────────────────────────────────────────────────────┐
│                      chat_service.py                          │
│  ┌───────────┐     ┌──────────────────────┐    ┌──────────┐ │
│  │ PostgreSQL │────▶│ compress_if_needed() │───▶│ LangGraph│ │
│  │ 加载全量  │     │  增量压缩服务         │    │  State   │ │
│  │ 消息历史  │     └───────────┬──────────┘    └──────────┘ │
│  └───────────┘                 │                             │
└────────────────────────────────┼─────────────────────────────┘
                                 │
                    ┌────────────┴────────────┐
                    ▼                         ▼
        ┌───────────────────┐    ┌───────────────────────┐
        │ context_compressor │    │   conversation_       │
        │ (LLM 摘要生成)     │    │   summaries 表        │
        │                   │    │   (摘要持久化)         │
        └───────────────────┘    └───────────────────────┘
```

设计的关键原则：**对 LangGraph 完全透明**。压缩逻辑作为中间件，在"加载历史"与"构建 State"之间执行，不侵入任何 Agent 节点代码。

### 3. 核心组件

| 组件 | 文件 | 职责 |
|------|------|------|
| 压缩调度服务 | `services/context_compression_service.py` | 四阶段决策逻辑，判断何时压缩、如何拼接 |
| LLM 压缩器 | `tools/context_compressor.py` | 调用 Qwen3 生成/融合摘要 |
| 摘要存储 | `db/models.py` (save/get_summary) | PostgreSQL 持久化摘要和元数据 |
| 数据库迁移 | `db/migrations/003_*.sql` | 为 conversation_summaries 添加 metadata 列 |

### 4. 数据流

```
用户发送第 N 轮消息
       │
       ▼
 PostgreSQL 加载全部 N 条历史消息
       │
       ▼
 compress_if_needed(session_id, all_messages)
       │
       ├── 路径A: N ≤ 20 且无缓存摘要 → 原样返回
       ├── 路径B: N ≤ 20 且有缓存摘要 → [摘要] + 最近消息
       ├── 路径C: N > 20 且无缓存摘要 → 首次压缩 → 保存摘要
       └── 路径D: N > 20 且有缓存摘要
              ├── 新增 ≤ 20 → 缓存摘要 + 新增消息
              └── 新增 > 20 → 增量再压缩(融合旧摘要 + 新消息)
       │
       ▼
 输出: [摘要 system 消息] + [最近 10 条原文消息]
       │
       ▼
 构建 LangGraph State，执行工作流
```

## 二、细节实现

### 1. 核心执行流程

#### 四阶段决策逻辑（`context_compression_service.py:24-105`）

```python
async def compress_if_needed(session_id, all_messages, user_id):
    total = len(all_messages)

    # 阶段 1: 消息数 ≤ 阈值
    if total <= COMPRESS_THRESHOLD:
        cached = await get_session_summary(sid)
        if cached:
            # 有历史摘要，拼接使用
            return [摘要消息] + all_messages[-10:]
        return all_messages  # 原样返回

    # 阶段 2-4: 消息数 > 阈值
    cached = await get_session_summary(sid)

    if cached:
        # 计算上次压缩覆盖的偏移量
        summarized_up_to = cached["metadata"]["summarized_up_to"]
        unsummarized = all_messages[summarized_up_to:]

        if len(unsummarized) <= COMPRESS_THRESHOLD:
            # 阶段 3: 新增未超阈值，直接用缓存
            return [摘要消息] + unsummarized[-10:]
        else:
            # 阶段 4: 增量再压缩（核心！）
            new_summary = await compress_messages(
                unsummarized[:-10],
                existing_summary=cached["summary"],  # 融合旧摘要
            )
            await save_summary(...)  # 更新偏移量
            return [新摘要消息] + unsummarized[-10:]
    else:
        # 阶段 2: 首次压缩
        new_summary = await compress_messages(all_messages[:-10])
        await save_summary(...)
        return [摘要消息] + all_messages[-10:]
```

**关键设计点**：
- `summarized_up_to` 字段记录摘要覆盖到第几条消息，实现增量计算
- 始终保留最近 10 条原文消息不压缩，确保 LLM 理解当前对话上下文
- 增量压缩时，将旧摘要作为 `existing_summary` 传入，LLM 在其基础上融合新消息

### 2. 关键技术实现

#### LLM 压缩 Prompt 设计（`context_compressor.py:20-32`）

```python
_COMPRESS_PROMPT = """你是一个对话摘要专家。请将以下对话历史压缩成一个简洁的摘要...

{existing_summary_section}  # 增量压缩时注入旧摘要

需要压缩的对话：
{conversation_history}

要求：
- 摘要不超过 400 字
- 保留：用户核心需求、已确认的偏好、已查询的信息、重要决策
- 丢弃：寒暄、重复确认、中间思考过程
"""
```

Prompt 设计要点：
- **明确的保留/丢弃规则**：指导 LLM 区分高价值信息和噪声
- **400 字上限**：确保摘要本身不会占用过多 Token
- **增量融合指令**：`existing_summary_section` 在增量模式下告诉 LLM 在旧摘要基础上合并

#### 消息预处理截断（`context_compressor.py:50-52`）

```python
content = msg["content"][:300] if len(msg.get("content", "")) > 300 else msg.get("content", "")
```

单条消息超过 300 字时截断，防止输入给压缩 LLM 的内容过长——这是一道**双重保护**：先截断单条消息，再由 LLM 压缩整体。

#### 摘要注入方式（`context_compression_service.py:117-119`）

```python
def _make_summary_message(summary: str) -> List[dict]:
    return [{"role": "system", "content": f"[对话摘要] {summary}"}]
```

摘要作为 `system` 角色消息注入，带 `[对话摘要]` 前缀标识，使下游 LLM 能区分摘要上下文和实时对话。

### 3. 异常与性能

#### 压缩失败容错（`context_compressor.py:78-82`）

```python
except Exception as e:
    if existing_summary:
        return existing_summary  # 降级：返回旧摘要
    return "（上下文压缩失败，已保留最近消息）"
```

- LLM 调用失败时不阻断主流程
- 有旧摘要则复用旧摘要（信息不丢失）
- 无旧摘要则返回占位文本（至少保留最近 10 条原文）

#### 数据库查询优化

```sql
-- 按 session 快速定位最新摘要（003 迁移创建）
CREATE INDEX idx_summaries_session
    ON conversation_summaries(session_id, created_at DESC);
```

- 复合索引支持 `ORDER BY created_at DESC LIMIT 1` 的高效查询
- 每个 session 只读取最新一条摘要，无需扫描全表

### 4. 技术难点

**难点 1：增量偏移量管理**

`summarized_up_to` 记录的是**绝对偏移量**（第 N 条消息），而非相对偏移。这样即使中间有消息删除/重生成，也能准确切分已压缩和未压缩的边界。

**难点 2：信息丢失与累积漂移**

多次增量压缩会导致信息逐步丢失（摘要的摘要）。通过以下策略缓解：
- 保留 400 字摘要上限，确保关键信息有足够空间
- 融合模式而非替换模式——新摘要在旧摘要基础上融合，而非独立压缩后替换
- 始终保留最近 10 条原文，确保当前上下文准确性

**难点 3：对 LangGraph 透明**

压缩服务的输出格式与原始消息列表完全兼容（`[{"role": ..., "content": ...}]`），`build_state_from_messages()` 无需任何修改即可处理压缩后的消息。

## 三、未来改进方向

### 1. 架构优化

| 当前问题 | 改进方案 | 预期收益 |
|---------|---------|---------|
| 每次请求都查 PG 获取摘要 | 用 Redis 缓存摘要（TTL = session 生命周期） | 减少 PG 查询延迟 ~5ms/次 |
| 压缩决策是硬编码阈值（20 条） | 基于 Token 数而非消息条数判断 | 更精确的压缩触发（短消息不浪费压缩） |
| 摘要是追加写入（INSERT），旧摘要不删 | 只保留最新摘要，旧摘要定期归档 | 减少存储膨胀 |

### 2. 性能与成本

| 当前问题 | 改进方案 | 预期收益 |
|---------|---------|---------|
| 每次增量压缩调用 LLM（~1-2s 延迟） | 异步后台压缩：先返回旧摘要+最近消息，后台完成压缩 | 减少用户感知延迟 |
| 压缩 LLM 使用同一个大模型（Qwen3） | 摘要生成用小模型（如 Qwen3-Mini），降低成本 | 摘要任务不需要强推理，小模型足够 |
| 单条消息截断 300 字较粗暴 | 按 Token 数截断，或按信息类型分级截断 | 保留更多关键信息 |

### 3. RAG / Memory 联动

| 当前问题 | 改进方案 | 预期收益 |
|---------|---------|---------|
| 压缩摘要未关联长期记忆 | 压缩时自动提取偏好/需求，写入 user_preferences | 跨会话信息保留 |
| 摘要是纯文本，不可结构化检索 | 压缩输出结构化 JSON（需求/偏好/已完成/待定） | 支持精准检索和条件筛选 |
| 摘要与 RAG 知识库割裂 | 历史摘要入库 Chroma，支持跨会话相似对话检索 | "上次你帮我规划的..."可被检索 |

### 4. 稳定性与评估

| 当前问题 | 改进方案 | 预期收益 |
|---------|---------|---------|
| 摘要质量无法量化 | 构建评估数据集：原始对话 → 压缩摘要 → 下游任务准确率 | 可量化压缩质量 |
| 无法感知信息丢失 | 引入"关键信息保留率"指标（key_points 对比） | 发现压缩质量退化 |
| 仅有 print 日志 | 接入 LangSmith trace，记录压缩前后 Token 数和延迟 | 可观测性 |

## 四、面试话术

### 1. 30 秒介绍

> 我在智慧出行 Agent 项目中设计并实现了增量上下文压缩策略。核心问题是：多轮对话场景下，如果每次请求携带全量历史消息，Token 成本会随轮次线性增长。我的方案是在消息加载和 LangGraph 执行之间插入一个透明的压缩层——首次超过阈值时用 LLM 生成摘要，之后每次只对新增消息做增量融合压缩，始终保留最近 10 条原文确保上下文准确。这样无论对话多长，实际输入给 LLM 的 Token 数保持恒定，约减少 60-80% 的上下文 Token 消耗。

### 2. 1～2 分钟完整介绍

> **业务背景**：我们的旅行规划 Agent 支持多轮对话，用户可能在一个会话里从选目的地、查交通、订酒店聊到行程确认，经常超过 20-30 轮。如果每轮都把全部历史传给 LLM，Token 成本不可控，而且长上下文会导致模型"迷失"关键信息。
>
> **架构设计**：我设计了一个对 LangGraph 完全透明的压缩中间件。它在 chat_service 加载完 PostgreSQL 的全量消息之后、构建 Graph State 之前执行。整个策略是四阶段决策：消息少于阈值不处理；超阈值无缓存摘要时做首次压缩；有缓存且新增消息少时直接复用；新增消息多时做增量再压缩。
>
> **核心实现**：增量压缩的关键是用 `summarized_up_to` 偏移量精确记录摘要覆盖到哪条消息，每次只对偏移量之后的新消息调用 LLM 压缩，并将旧摘要作为上下文让 LLM 做融合式压缩而非覆盖式。摘要固定在 400 字以内，作为 system 消息注入，始终保留最近 10 条原文保证 LLM 能理解当前对话上下文。
>
> **技术难点**：一是信息累积丢失问题——多次"摘要的摘要"会逐步丢失细节，通过融合模式而非独立压缩来缓解；二是容错——LLM 调用失败时降级为旧摘要，不阻断主流程；三是对下游完全透明——输出格式与原始消息列表兼容，LangGraph 无需任何修改。
>
> **最终效果**：无论对话长度，输入到主 LLM 的上下文始终在"1 条摘要 + 10 条原文"的范围内，Token 消耗从 O(n) 降为 O(1)，预估节省 60-80% 上下文 Token。

### 3. 技术亮点

1. **对工作流完全透明的中间件设计**：压缩服务对 LangGraph 零侵入，插拔自如，任何 Agent 节点无需感知压缩的存在
2. **增量融合压缩算法**：通过 `summarized_up_to` 偏移量追踪 + LLM 融合模式，实现 O(1) 上下文成本
3. **四阶段决策策略**：精确判断何时需要压缩、何时复用缓存，避免不必要的 LLM 调用
4. **优雅降级机制**：LLM 压缩失败时自动降级（复用旧摘要 / 保留最近消息），不阻断主流程
5. **Prompt 工程的信息保留/丢弃规则**：明确指导 LLM 保留核心需求和决策、丢弃寒暄和重复，平衡压缩率与信息完整性

### 4. 面试官可能追问

#### Q1：为什么不直接截断旧消息，而要用 LLM 压缩？

**考察点**：对信息丢失和上下文质量的理解

**推荐回答**：
> 简单截断（如只保留最近 N 条）会丢失关键的早期信息——比如用户第 3 轮说的"预算 5000 以内"、第 5 轮确认的"不要太赶的节奏"。这些信息在后续规划中至关重要。LLM 压缩的优势是能**语义理解后选择性保留**：核心需求、偏好、已确认的决策都保留，只丢弃寒暄和重复确认这类低价值内容。

**追问**：那为什么不用 embedding 做 top-K 相关消息检索？
> 可以结合使用，但纯检索方式缺乏对话连贯性——它能找到"相关的"消息但无法保持逻辑链。摘要则保留了因果链和决策脉络。理想方案是摘要 + 检索混合。

---

#### Q2：增量压缩时信息会不会越压越少，最终丢失关键内容？

**考察点**：对信息熵衰减问题的认识和解决方案

**推荐回答**：
> 确实存在"摘要的摘要"导致信息逐步丢失的问题。我的缓解策略有三个：
> 1. **融合模式**而非独立压缩——增量压缩时旧摘要作为上下文传入，LLM 是在旧摘要基础上融合新信息，而非独立压缩后替换
> 2. **400 字摘要上限**给关键信息足够空间，不过度压缩
> 3. **始终保留最近 10 条原文**，确保当前对话上下文完整
>
> 未来计划引入结构化摘要（需求/偏好/决策分字段），让关键信息以 key-value 形式保留，避免纯文本摘要的信息丢失。

---

#### Q3：为什么用消息条数（20 条）作为阈值，而不是 Token 数？

**考察点**：工程决策的权衡能力

**推荐回答**：
> 当前用消息条数是 MVP 阶段的简化选择——实现简单且可预测。Token 计数需要引入 tokenizer（不同模型 tokenizer 不同），增加依赖和计算开销。实际测试中，旅行对话的平均消息长度比较稳定（100-300 字/条），20 条约对应 4000-8000 Token，对 Qwen3 的 32K 窗口来说是合理的触发点。后续优化会改为基于 Token 数的阈值。

---

#### Q4：如何保证压缩对 LangGraph 透明？

**考察点**：中间件设计能力

**推荐回答**：
> 透明性体现在三个层面：
> 1. **接口兼容**：压缩函数输入是 `List[dict]`，输出也是 `List[dict]`，格式完全一致
> 2. **调用位置**：只在 chat_service 的一个调用点（加载历史之后、构建 State 之前），不侵入任何 Agent 节点
> 3. **摘要注入方式**：作为 system 消息注入，下游 `build_state_from_messages` 函数将其正常处理为对话上下文的一部分
>
> 如果要关闭压缩功能，只需删除 `compress_if_needed` 这一行调用即可。

---

#### Q5：如果 LLM 压缩服务出现延迟或失败，怎么处理？

**考察点**：容错和可用性设计

**推荐回答**：
> 我设计了三层容错：
> 1. **失败降级**：LLM 调用异常时，如果有旧摘要则返回旧摘要（信息不丢失），无旧摘要则返回占位提示
> 2. **缓存复用**：如果新增消息未超阈值，直接复用 PostgreSQL 中的缓存摘要，完全跳过 LLM 调用
> 3. **最坏情况兜底**：即使压缩完全失败，最近 10 条原文消息仍然保留，用户的当前对话不受影响
>
> 实际场景中，压缩 LLM 调用只在新增消息超阈值时触发，大部分请求走缓存复用路径，延迟影响有限。

### 5. 重点问题参考答案

#### 如何评估压缩策略的效果？

> 三个维度：
> 1. **Token 节省率**：压缩前后输入 Token 数对比，目标 >60%
> 2. **下游任务准确率**：用相同问题对比"全量上下文" vs "压缩后上下文"的回答质量（人工评估）
> 3. **关键信息保留率**：标注对话中的关键信息点，检查压缩后是否保留

目前通过 print 日志观察压缩率，后续计划接入 LangSmith 做系统化评估。

#### 为什么不用 LangChain 内置的 ConversationSummaryBufferMemory？

> LangChain 的内置方案有几个限制：
> 1. 不支持持久化——摘要存在内存中，服务重启丢失
> 2. 不支持增量融合——每次都全量重新压缩
> 3. 与我们的 PostgreSQL + 分层记忆架构不兼容
>
> 自研方案能与现有的 conversation_summaries 表、三层记忆系统深度集成，实现跨请求缓存复用和增量压缩。
